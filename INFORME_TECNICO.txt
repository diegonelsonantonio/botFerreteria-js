RESUMEN EJECUTIVO
--------------------------------------------------------------------------------
Bot Ferretería es un sistema de chatbot inteligente diseñado para automatizar
la atención al cliente en el sector ferretero. Integra tecnologías de IA
avanzadas (OpenAI GPT-4) con arquitectura serverless para proporcionar
respuestas contextuales, búsqueda semántica de productos y gestión de pedidos
a través de WhatsApp y Facebook Messenger.

El sistema implementa patrones de diseño modernos, arquitectura en capas y
mejores prácticas de desarrollo, resultando en una solución escalable,
mantenible y de alto rendimiento.

ARQUITECTURA DEL SISTEMA
--------------------------------------------------------------------------------

Patrón Arquitectónico: Arquitectura en Capas (Layered Architecture)

El sistema está organizado en cuatro capas principales con separación clara
de responsabilidades:

1. API LAYER (Capa de Presentación)
   Responsabilidad: Manejo de requests HTTP y respuestas
   Componentes:
   - Controllers: Lógica de endpoints
   - Routes: Definición de rutas
   - Middlewares: Procesamiento de requests

2. BUSINESS LOGIC LAYER (Capa de Negocio)
   Responsabilidad: Lógica de negocio y orquestación
   Componentes:
   - Services: Servicios de negocio
   - Context Management: Gestión de estado conversacional

3. DATA ACCESS LAYER (Capa de Datos)
   Responsabilidad: Acceso y persistencia de datos
   Componentes:
   - Repositories: Abstracción de acceso a datos
   - Models: Esquemas y validación

4. EXTERNAL SERVICES LAYER (Capa de Servicios Externos)
   Responsabilidad: Integración con servicios de terceros
   Componentes:
   - OpenAI Client
   - Pinecone Client
   - Meta API Client

Flujo de Datos:
Usuario → Meta API → Webhook → Controller → Service → Repository → Database
                                    ↓
                              OpenAI/Pinecone
                                    ↓
                              Response → Meta API → Usuario

PATRONES DE DISEÑO IMPLEMENTADOS
--------------------------------------------------------------------------------

1. REPOSITORY PATTERN
   Ubicación: src/core/repositories/
   Propósito: Abstraer el acceso a datos
   Beneficios:
   - Desacoplamiento de la fuente de datos
   - Facilita testing con mocks
   - Centraliza queries complejas

2. SERVICE LAYER PATTERN
   Ubicación: src/core/services/
   Propósito: Encapsular lógica de negocio
   Beneficios:
   - Lógica reutilizable
   - Fácil de testear
   - Separación de concerns

3. MIDDLEWARE PATTERN
   Ubicación: src/api/middlewares/
   Propósito: Procesamiento de requests
   Beneficios:
   - Código modular
   - Reutilizable
   - Fácil de mantener

4. CONTEXT PATTERN
   Ubicación: src/core/context/
   Propósito: Mantener estado conversacional
   Beneficios:
   - Conversaciones contextuales
   - Memoria entre interacciones
   - Personalización por usuario

5. DEPENDENCY INJECTION
   Implementación: Módulos ES6
   Beneficios:
   - Bajo acoplamiento
   - Alta cohesión
   - Testeable

DESCRIPCIÓN DETALLADA DE COMPONENTES
--------------------------------------------------------------------------------

API LAYER (src/api/)
--------------------

webhook.controller.js
  Función: Controlador principal para webhooks de Meta
  Responsabilidades:
    - Verificar webhook inicial (GET /webhook)
    - Recibir mensajes de usuarios (POST /webhook)
    - Extraer datos de eventos de Meta
    - Delegar procesamiento a servicios
  Endpoints:
    GET  /webhook  - Verificación de webhook
    POST /webhook  - Recepción de mensajes
  Decisiones de Diseño:
    - Responde 200 OK inmediatamente (requisito de Meta < 20s)
    - Procesamiento asíncrono de mensajes
    - Maneja texto y Quick Replies

metaVerify.js
  Función: Middleware de seguridad
  Responsabilidades:
    - Verificar firma HMAC SHA-256 de Meta
    - Prevenir requests no autorizados
    - Validar integridad del payload
  Algoritmo:
    1. Extraer firma del header X-Hub-Signature-256
    2. Calcular HMAC del body con APP_SECRET
    3. Comparar firmas
    4. Rechazar si no coinciden
  Seguridad: Previene ataques de replay y spoofing

errorHandler.js
  Función: Manejo centralizado de errores
  Responsabilidades:
    - Capturar errores no manejados
    - Formatear respuestas de error
    - Logging de errores
    - Prevenir exposición de detalles internos

webhook.routes.js
  Función: Definición de rutas
  Configuración:
    - express.raw() para body sin parsear (requerido para firma)
    - Aplicación de middlewares en orden
    - Delegación a controllers

BUSINESS LOGIC LAYER (src/core/)
---------------------------------

message.service.js
  Función: Orquestador principal de mensajes
  Responsabilidades:
    - Obtener contexto conversacional
    - Determinar intención del usuario
    - Buscar información relevante (RAG)
    - Generar respuesta con IA
    - Enviar respuesta a Meta
    - Actualizar contexto
  Flujo:
    Usuario → Contexto → RAG → GPT-4 → Respuesta → Meta → Usuario
  Decisiones:
    - Payloads para acciones específicas
    - RAG solo para consultas generales
    - Contexto persistente entre mensajes

order.service.js
  Función: Gestión de pedidos
  Responsabilidades:
    - Crear nuevos pedidos
    - Validar stock disponible
    - Calcular totales
    - Actualizar estado de pedidos
    - Consultar historial
  Validaciones:
    - Stock suficiente
    - Precios actualizados
    - Usuario válido
    - Productos existentes

rag.service.js
  Función: Búsqueda semántica con RAG
  Responsabilidades:
    - Crear embeddings de queries
    - Buscar en Pinecone
    - Rankear resultados por relevancia
    - Retornar contexto para GPT-4
  Proceso:
    1. Query → Embedding (OpenAI)
    2. Embedding → Búsqueda (Pinecone)
    3. Resultados → Contexto
  Ventajas:
    - Respuestas basadas en información real
    - Reduce alucinaciones de GPT-4
    - Actualizable sin reentrenar

conversationContext.js
  Función: Gestión de estado conversacional
  Responsabilidades:
    - Mantener historial de mensajes
    - Trackear estado de conversación
    - Limpiar contextos antiguos
  Implementación Actual:
    - Map() en memoria (limitación: no escala horizontalmente)
  Mejora Recomendada:
    - Redis para contexto distribuido

FLUJO COMPLETO DE UN MENSAJE
-----------------------------

1. RECEPCIÓN
   Usuario envía mensaje en WhatsApp
   ↓
   Meta envía POST a https://tu-dominio.run.app/webhook
   Headers: X-Hub-Signature-256 (firma HMAC)
   Body: JSON con evento de mensaje

2. VALIDACIÓN
   Middleware metaVerify.js
   ↓
   Verifica firma HMAC SHA-256
   ↓
   Si válida: continúa | Si inválida: 403 Forbidden

3. CONTROLADOR
   webhook.controller.postWebhook()
   ↓
   Responde 200 OK inmediatamente a Meta
   ↓
   Extrae: senderId, messageText, payload
   ↓
   Llama a processMessage() de forma asíncrona

4. PROCESAMIENTO
   message.service.processMessage()
   ↓
   a) Obtiene contexto conversacional
      conversationContext.getContext(senderId)
      ↓
      Retorna: { messages: [], lastInteraction, state }
   
   b) Determina intención
      Si payload === 'MENU_PRODUCTOS' → handleProductsMenu()
      Si payload === 'MENU_PEDIDOS' → handleOrdersMenu()
      Si no → Procesamiento con IA
   
   c) Búsqueda RAG (si aplica)
      rag.service.searchKnowledge(messageText)
      ↓
      Crea embedding con OpenAI
      ↓
      Busca en Pinecone (top 5 resultados)
      ↓
      Retorna documentos relevantes
   
   d) Generación de respuesta
      openai.chat.completions.create()
      ↓
      Model: gpt-4
      Messages: [system, ...context, user, knowledge]
      ↓
      Retorna respuesta generada
   
   e) Envío a usuario
      Meta Graph API
      ↓
      POST /me/messages
      ↓
      Body: { recipient, message, quick_replies }
   
   f) Actualización de contexto
      conversationContext.updateContext()
      ↓
      Agrega mensaje de usuario y bot al historial
      ↓
      Actualiza timestamp

5. RESPUESTA
   Usuario recibe mensaje en WhatsApp

FLUJO DE CREACIÓN DE PEDIDO
----------------------------

1. Usuario: "Quiero comprar martillo"
   ↓
2. Bot busca en MongoDB
   Product.find({ name: /martillo/i })
   ↓
3. Bot: "Encontré: Martillo $150. ¿Confirmas?"
   Quick Reply: [Sí] [No]
   ↓
4. Usuario: [Sí]
   ↓
5. order.service.createOrder()
   ↓
   a) Valida stock
      Product.findById(productId)
      if (product.stock < quantity) throw Error
   
   b) Crea documento
      Order.create({
        userId,
        products: [{ productId, name, quantity, price }],
        total,
        status: 'pending'
      })
   
   c) Actualiza stock
      Product.updateOne(
        { _id: productId },
        { $inc: { stock: -quantity } }
      )
   
   d) Genera número de orden
      orderId = order._id
   ↓
6. Bot: "Pedido #12345 creado. Total: $150"

DECISIONES TÉCNICAS Y JUSTIFICACIONES
--------------------------------------------------------------------------------

1. ¿POR QUÉ MONGODB?
   Razones:
   - Esquema flexible: Fácil evolucionar modelos sin migraciones
   - Documentos anidados: Pedidos con productos embebidos
   - Escalabilidad horizontal: Sharding nativo
   - Atlas: Managed service con backups automáticos
   - Mongoose: ODM robusto con validación
   
   Alternativas Consideradas:
   - PostgreSQL: Más rígido, requiere migraciones
   - DynamoDB: Vendor lock-in con AWS
   - Firebase: Menos control, costos variables

2. ¿POR QUÉ OPENAI GPT-4?
   Razones:
   - Calidad: Mejores respuestas conversacionales
   - Contexto: 128k tokens de contexto
   - Multimodal: Soporte futuro para imágenes
   - API Simple: Fácil integración
   - Español: Excelente soporte del idioma
   
   Alternativas Consideradas:
   - Claude (Anthropic): Bueno pero menos disponible
   - Llama 2: Requiere hosting propio
   - Gemini: Menos maduro en español

3. ¿POR QUÉ PINECONE?
   Razones:
   - Managed: No requiere infraestructura
   - Rápido: Búsqueda < 100ms
   - Escalable: Millones de vectores
   - Metadata Filtering: Filtros avanzados
   
   Alternativas Consideradas:
   - Weaviate: Requiere self-hosting
   - Qdrant: Menos maduro
   - pgvector: Limitado en escala

4. ¿POR QUÉ EXPRESS.JS?
   Razones:
   - Minimalista: Solo lo necesario
   - Middleware: Ecosistema rico
   - Maduro: Estable y probado
   - Documentación: Excelente
   
   Alternativas Consideradas:
   - Fastify: Más rápido pero menos maduro
   - NestJS: Demasiado complejo para este caso
   - Koa: Menos ecosistema

5. ¿POR QUÉ GOOGLE CLOUD RUN?
   Razones:
   - Serverless: No gestionar servidores
   - Escala a Cero: Ahorro de costos
   - Contenedores: Flexibilidad total
   - Integración: Fácil con otros servicios GCP
   - Precio: Pay-per-use
   
   Alternativas Consideradas:
   - AWS Lambda: Límites de tiempo de ejecución
   - Heroku: Más caro
   - VPS: Requiere mantenimiento

6. ¿POR QUÉ ARQUITECTURA EN CAPAS?
   Razones:
   - Separación de concerns
   - Fácil de entender
   - Mantenible
   - Testeable
   - Escalable
   
   Ventajas:
   - Cada capa tiene responsabilidad única
   - Cambios en una capa no afectan otras
   - Fácil agregar nuevas features
   - Testing por capas

SEGURIDAD
--------------------------------------------------------------------------------

MEDIDAS IMPLEMENTADAS
----------------------

1. Verificación de Firma HMAC SHA-256
   Ubicación: src/api/middlewares/metaVerify.js
   Algoritmo:
     signature = HMAC-SHA256(body, APP_SECRET)
     if (signature !== header['X-Hub-Signature-256']) reject
   Previene: Ataques de replay, spoofing

2. Variables de Entorno
   Ubicación: .env (no commiteado)
   Contenido:
     - Credenciales de Meta
     - API keys de OpenAI
     - Strings de conexión de MongoDB
   Protección: .gitignore, Secret Manager en producción

3. HTTPS Obligatorio
   Proveedor: Google Cloud Run
   Certificado: Automático (Let's Encrypt)
   Previene: Man-in-the-middle attacks

4. Validación de Input
   Ubicación: Controllers y Services
   Validaciones:
     - Sanitización de mensajes de usuario
     - Validación de payloads
     - Límites de tamaño
   Previene: Injection attacks, XSS

5. Manejo Seguro de Errores
   Ubicación: src/api/middlewares/errorHandler.js
   Comportamiento:
     - No expone stack traces en producción
     - Logging interno de errores
     - Mensajes genéricos al usuario
   Previene: Information disclosure

RECOMENDACIONES ADICIONALES
----------------------------

1. Rate Limiting
   Herramienta: express-rate-limit
   Configuración:
     - 100 requests por 15 minutos por IP
     - 429 Too Many Requests si excede
   Previene: DDoS, abuso de API

2. Helmet.js
   Función: Headers de seguridad HTTP
   Headers:
     - X-Content-Type-Options: nosniff
     - X-Frame-Options: DENY
     - Strict-Transport-Security
   Previene: Clickjacking, MIME sniffing

3. Input Validation con express-validator
   Validaciones:
     - Tipo de datos
     - Formato
     - Rangos
   Previene: Injection, data corruption

4. Secret Manager en Producción
   Proveedor: Google Cloud Secret Manager
   Ventajas:
     - Encriptación en reposo
     - Rotación automática
     - Auditoría de accesos
   Implementación: deploy-secrets.ps1

5. Logging Seguro
   Reglas:
     - NO logear credenciales
     - NO logear datos personales completos
     - Usar IDs en lugar de datos sensibles
   Herramienta: Winston (recomendado)

ESTRATEGIAS DE ESCALABILIDAD
-----------------------------

1. Escalado Horizontal (Actual)
   Mecanismo: Cloud Run auto-scaling
   Trigger: CPU > 60% o Requests > 80 por instancia
   Límite: 10 instancias (configurable)

2. Redis para Contexto (Recomendado)
   Problema: Map() no escala horizontalmente
   Solución: Redis compartido entre instancias
   Beneficios:
     - Contexto distribuido
     - TTL automático
     - Persistencia opcional
   Costo: ~$10/mes

3. Queue System (Recomendado)
   Problema: Procesamiento síncrono puede ser lento
   Solución: Bull Queue con Redis
   Beneficios:
     - Respuesta inmediata a Meta
     - Retry automático
     - Priorización
     - Múltiples workers
   Costo: Incluido en Redis

4. Cache de Embeddings (Recomendado)
   Problema: Crear embeddings es costoso
   Solución: Cache en Redis con hash del texto
   Beneficios:
     - Ahorro ~90% de llamadas a OpenAI
     - Respuestas más rápidas
   Ahorro: ~$50/mes

5. CDN para Assets
   Problema: Imágenes de productos lentas
   Solución: Cloud Storage + CDN
   Beneficios:
     - Carga rápida de imágenes
     - Reducción de latencia
   Costo: ~$5/mes
